What it is
## A place for every useful agent.
Build for a real problem in any domain: payments, training, evaluation, operations, research, or something new. There is no prescribed architecture or required zkVerify integration. Explain your use case and show the agent working.

01

### Pick a real problem
Choose the people or workflow your agent serves. A clear use case matters more than fitting a preset category.
02

### Show the agent working
Share a public link and endpoint so reviewers can understand the build and see what it can do.
03

### Add proof if it helps
A thoughtful zkVerify use case can strengthen your entry. If you include a proof, explain exactly what it establishes.

What to include
## Submission requirements

AGENT LINK
A public repository, demo, or write-up showing the agent you built.

PUBLIC ENDPOINT
A public HTTPS endpoint for your agent, as requested in the submission form.

USE CASE
Explain the problem, who the agent helps, and what it actually does.

BUILD CONTEXT
Briefly describe how the agent works and the key decisions behind it.

ZKVERIFY (OPTIONAL)
If zkVerify strengthens your agent, explain the checkable claim and add a proof reference when available.

How work is judged
## What reviewers look for

### Useful problem
Show a clear need, who the agent helps, and why its work matters.

### Working implementation
Make it possible to understand what you built and see the agent in action.

### Clear explanation
Explain the workflow, key choices, and what the agent can and cannot do.

### Verifiability (optional plus)
If zkVerify makes an important claim checkable, explain how it helps. Agents without zkVerify remain eligible.

Inspiration
## Many use cases are welcome
These are starting points, not a checklist. Submit an agent in any domain where it can solve a real problem; the zkVerify example is one optional direction.

### zkTLS — prove what your agent saw on the webSuggested direction
A strong optional way to earn the verifiability plus: use zkTLS to turn a real HTTPS or API response your agent relied on into a zkVerify-checkable claim — without revealing the full payload. It is a suggestion, not a requirement.

PAYMENTS
### Agentic payment workflows
An agent that prepares invoices, compares terms, and routes a payment for approval.
TRAINING
### Training and evaluation
An agent that runs scenarios, assesses results, and helps improve another agent's behaviour.
OPERATIONS
### Useful everyday workflows
An agent that coordinates tools and tasks to solve a practical problem for its users.
VERIFIABILITY
### A provable agent claim
An agent that uses zkVerify to make one important result independently checkable.
ZKTLS
### Prove what your agent saw
Use zkTLS to make the web or API data your agent acted on independently checkable through zkVerify — without exposing the raw response.
